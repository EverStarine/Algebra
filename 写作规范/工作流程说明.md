# 《代数学》项目工作流程

版本：2.0（2026-09-23）

本文件主管任务定界、编辑顺序、构建核验、工作记录、临时文件和版本管理。数学内容、排版、术语和书目细节分别由其他规范主管；本文件只说明何时调用它们以及为什么。

## 1. 主管文件与单一真源

| 内容 | 主管文件 | 设立原因 |
|---|---|---|
| 卷、编、章、节标题，选读范围，所需基础与证明归属 | `工作记录/计划纲要.md` | 目录和知识依赖必须只有一个权威来源，避免正文与计划各自演变。 |
| 教材组织、证明职责、习题和行文 | `写作规范/写作规范.md` | 内容质量规则不应混入 TeX 或操作流程。 |
| 文件结构、编号、标签、字体、公式和输出 | `写作规范/格式规范.md` | 排版接口集中管理，才能让五卷保持一致。 |
| 主称、原文、数学约定、记号和索引收词 | `写作规范/术语规范.md` | 术语和符号跨卷复用，需要独立维护。 |
| 正式书目资格、BibLaTeX 字段和版本证据 | `写作规范/书目维护注意事项.md` | 结构化书目数据不能靠正文写作规则代管。 |
| 当前完成度和正式审核轮数 | `工作记录/审核进度.md` | 状态必须与修改过程分开，避免历史流水淹没当前结论。 |
| 实际跨卷调用及证明状态 | `工作记录/跨卷引用表.md` | 五卷独立 PDF 无法用普通内部引用自动保证目标真实存在。 |
| 构建入口和当前工程说明 | `README.md` 与构建脚本 | 命令以可执行工程为准，规范不复制易漂移的参数。 |
| 作者身份、许可和材料使用边界 | `版权声明.md` | 权利边界不应由技术流程临时决定。 |

同一规则只在主管文件完整表述，其他文件用链接或简短回指。原因是重复规则最容易在后续修订中出现冲突。

## 2. 开始任务

| 规则 | 设立原因 |
|---|---|
| 先查看工作区状态，确认用户指定的卷、章、文件和任务类型。 | 工作区可能已有未提交修改；先定界可避免覆盖他人工作或扩大任务。 |
| 阅读目标位置的纲要、相邻正文和相关规范，再决定修改范围。 | 数学定义、文风和文件层级通常依赖上下文，不能只凭孤立片段处理。 |
| 有 TeX 源码时以源码为准；PDF 只用于成品与版面核验。 | PDF 不能可靠显示标签、证明依赖、注释和输入关系。 |
| 将“解释或审稿”与“授权修改”区分；用户只要求评估时不直接改稿。 | 分析结论不自动授予修改权限。 |
| 《写作规范》界定的重大结构调整，在实施前完成方案说明和作者确认。 | 内容规范主管“哪些改动必须商议”，流程只负责确保确认发生在编辑之前。 |

## 3. 编辑与写作顺序

| 步骤 | 规则 | 设立原因 |
|---:|---|---|
| 1 | 按纲要确定本轮应完成的定义、构造、定理、例子、习题和边界。 | 先明确承诺，才能判断是否真正完成，而不是只扩写提纲。 |
| 2 | 核对先修、假设、左右作用、底环或基域、特征和有限性。 | 这些条件常决定陈述真假，也最容易在跨章调用中丢失。 |
| 3 | 新术语和稳定记号先查《术语规范》；新增或改名时记录主称、原文、范围、异名和证据，并检索五卷既有用法。 | 局部命名会传播到目录、索引和后卷；记录证据范围可避免把暂用名称误作已核定主称。 |
| 4 | 按“问题—对象—构造—证明—算例”组织正文，并遵守《写作规范》的环境职责。 | 这一顺序使抽象理论有动机、有定义且可检验，同时不要求每节机械同形。 |
| 5 | 为正式结构、数学环境、必要公式和可引用列表项设置稳定标签。 | 稳定标签是证明回引、审稿定位和跨卷维护的基础。 |
| 6 | 完成章末小结、代表习题及解答或明确提示。 | 教材完成度包括训练与反馈，不能只看正文定理。 |
| 7 | 修改后同步纲要标题、输入链、当前状态和实际跨卷引用。 | 结构和证明位置变化若不同步，会产生错误导航或循环依赖。 |

根文件装配全卷，编文件装配各章，章文件承载章级内容及节入口，节文件是正文最小文件层级，共享样式只改 `Shared/`。原因是明确所有权可以避免重复定义和失效输入。

## 4. 处理审稿与数学疑点

| 规则 | 设立原因 |
|---|---|
| 逐条对照审稿意见与当前源码，先判断意见是否仍适用，再修改。 | 报告可能依据旧版本，不能机械套用行号和原文。 |
| 数学修改追踪定义、假设、被引结果和后续调用，不只修被指出的一句。 | 局部改动可能改变整条证明链。 |
| 模型建议、外部检索、符号计算和有限算例只作为相应范围的证据。 | 工具输出不能自动替代一般证明或人工术语判断。 |
| 无法判断的作者取舍、数学结论或结构目的应明确提问，不以猜测补齐。 | 保留疑问比制造虚假的一致性更安全。 |
| 尚未解决的问题保留真实状态，不写成“已闭环”“已定稿”。 | 审核记录必须反映事实，编译成功也不证明数学正确。 |
| 审稿处理后更新逐章状态表；具体修改过程留在审稿意见、专项记录或 Git 历史，不写入长篇进度流水。 | 当前状态要易于查阅，细节又需要有合适的证据载体。 |

## 5. 文献与跨卷调用

| 规则 | 设立原因 |
|---|---|
| 新文献先按《书目维护注意事项》确认资格、版本和定位，再进入正式 Bib 和正文。 | 能编译的条目不一定真实、版本一致或支持所引结论。 |
| 本地第三方资料放在 `参考文献原文件/`，不随源码提交或上传。 | 教材仓库没有自动重新分发第三方全文的授权。 |
| 新取得资料在 `工作记录/参考资料目录.md` 登记来源、版本、取得日期、实际阅读范围和使用位置；存在本地文件时另记可复核的文件身份或哈希，不以无法取得或未经核验的旧库存清单代替现行登记。 | 统一的现行记录是跨环境可见的长期入口；版本和阅读范围可防止把“已下载”误写成“已核读”。 |
| 同一资料出现新版或不同网络快照时先比较版本，不静默覆盖旧文件；一份资料供多卷使用时不重复复制。 | 保留版本差异才能追踪页码和结论来源，去重可减少哈希与路径漂移。 |
| 参考资料库安装完整时，按 README 调用现有 `scripts/Check-ReferenceLibrary.py` 检查文件和登记信息；若库存清单缺失，只报告可完成的检查范围，不声称全库已验证。 | 自动检查适合发现丢失或错配文件，但缺少输入清单时不能产生完整性结论。 |
| 实际跨卷调用同步登记引用处、目标、稳定标签、内容和证明状态。 | 五卷独立编译，必须另行记录目标是否已证明。 |
| 区分“已证调用”“前瞻陈述”和“计划位置”。 | 目录中的未来章节不能成为当前证明的隐含前提。 |

## 6. 构建与核验

| 规则 | 设立原因 |
|---|---|
| 使用 `README.md` 规定的构建脚本；只改一卷正文时构建该卷，修改共享样式或构建逻辑时构建五卷。 | 验证范围应与影响范围一致，既避免漏检也避免无谓重编。 |
| 只改说明或规范且未改变源码规则时，不机械重编 PDF。 | 文档维护不会改变排版产物，重编没有新增证据。 |
| 构建失败先看首个有效错误，再处理后续连锁报错。 | 后续错误常是首错造成的噪声。 |
| 优先修复现有 TeX Live、命令路径和配置，不为普通故障另装工具链。 | 多套工具链会增加版本差异，并违背项目复用现有安装的约定。 |
| 最终核对编译错误、未定义引用或引文、重复标签、重跑提示、缺字、索引拒收和 Overfull。 | 这些项目会直接导致错误内容、失效链接或版心溢出。 |
| Underfull 等非致命提示按具体页面判断，不把“构建成功”写成“零警告”。 | 日志级别不同，笼统宣称无警告会掩盖实际残留。 |
| 验证以 TeX 源码、编译报错和日志为主。仅在交换图、绘图、大型表格、用户指出的显示问题或日志无法判断的具体疑点处定向渲染。 | 视觉检查应解决明确问题，不应成为每轮审稿的高成本例行步骤。 |
| 构建失败或引用、索引尚未稳定时，不用旧 PDF 冒充新成品。 | 交付物必须对应当前源码并通过当前验证。 |
| 结构、标签和输入链用 `scripts/Check-Outline.ps1` 等现有只读检查核验。 | 自动检查适合发现机械不一致，但不能替代数学审稿。 |

构建辅助文件统一放在 `tmp/build/BookN/`，成功后由脚本更新根目录 PDF 和卷目录预览。原因是隔离辅助文件可保持源码目录整洁，并防止旧 `.aux`、`.bbl` 或索引文件污染结果。

## 7. 工作记录与临时文件

| 规则 | 设立原因 |
|---|---|
| `工作记录/审核进度.md` 先列分卷与逐章表，阶段过程只保留粗略里程碑。 | 使用者首先需要当前状态，而不是按日期翻找结论。 |
| 每个阶段里程碑只记录范围、结果、验证状态和未决项。 | 足以恢复决策，同时避免重复源码和审稿报告中的细节。 |
| 一般检查在回复中说明；只有跨轮次仍有价值的结论才写入已有记录。 | 防止为每次修改制造新的报告文件。 |
| 临时统计、截图、渲染和一次性脚本放入 `tmp/`。 | 这些产物可重建，不应与长期源码混放。 |
| 清理只针对已核实路径中的可重建产物，不递归删除工作区或资料库。 | 未提交正文和参考资料可能无法恢复。 |
| 可复现的长期工具故障只记录首个错误、根因、处理和验证。 | 保留可复用知识即可，无需保存完整调试流水。 |

## 8. Git 与 GitHub

| 规则 | 设立原因 |
|---|---|
| 日常修改默认只在本地编辑、构建和核验；只有用户明确要求时才提交或上传。 | 一次上传授权不应被解释为永久自动发布。 |
| 提交前检查状态和差异，只纳入本次授权范围及必要成品。 | 工作区可能同时包含用户或其他任务的修改。 |
| 不提交 `tmp/`、辅助文件、凭据或第三方参考全文。 | 这些文件要么可重建，要么存在安全与版权风险。 |
| 推送前核对仓库和分支，推送后核对远端提交。 | 本地提交成功不等于上传到正确目标。 |
| 遇到非快进冲突先检查远端变化，不强制推送或批量回退。 | 强制操作可能清除他人提交或未保存工作。 |

## 9. 已知工具链例外

| 现象与处理 | 设立原因 |
|---|---|
| XeTeX 在当前字体配置下处理单字符 `\widehat{\mathbb Z}` 可能触发 `bad native font flag in map_char_to_glyph`；使用 `\widehat{\vphantom{Z}\mathbb Z}`。 | 该写法已在最小文档和整卷中验证，能绕开引擎路径且不更换字体、引擎或数学含义。 |
